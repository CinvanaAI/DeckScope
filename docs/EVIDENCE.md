# Evidence: frozen corpora and claim-blind discovery

Two design changes that between them make the architecture testable rather than
merely plausible.

---

## The problem with a claim-directed market pass

DeckScope's market analyst is given the deck's claims. It has to be — it is checking
them. But that shapes what it searches for, and the consequence is asymmetric:

> **Claim-directed research finds errors well and finds omissions badly.**
> Nobody searches for what they were not prompted to consider.

If a deck names Zapier and Make as its competitors, the research agenda asks about
Zapier and Make. If the deck never mentions that ServiceNow already owns the workflow
layer in every company running ITSM, nothing in the pipeline is likely to ask.

That is the exact failure the report's "blind spots" section is supposed to catch, and
it was being generated by the same anchored process that created the gap.

## The fix: research the category cold

```bash
deckscope run deck.pdf --cold-discovery
deckscope demo --cold-discovery        # free, illustrative
```

A second pass receives **only the category, sub-category, geography and company name**
and never sees a single claim. It writes its own queries, reads its own sources, and
describes the market as an analyst would who was handed the beat on their first day.

Then DeckScope diffs the two routes. What appeared on the cold route and not the
directed one is a blind spot that *no prompt could have produced*, because the process
that found it could not have been anchored by the deck.

### The isolation is structural, not instructional

A system prompt saying "you have not seen the deck" is worth very little when the deck
is in the context window. So the boundary is a function:

```python
ALLOWED_IDENTITY_FIELDS = ("category", "sub_category", "geography")

@staticmethod
def _identity(deck):
    """Everything this agent is allowed to know. Nothing else may pass."""
```

A **whitelist, not a blacklist** — a blacklist grows a hole every time the deck schema
gains a field. And a test asserts on the payload rather than on the prompt: it builds a
deck containing a TAM claim, traction figures, an ask, named competitors and founder
names, and asserts that none of those strings can appear in what the agent receives.
There is a second test proving that a newly added deck field cannot leak by default.

A company **name** is included, because a market cannot be researched without knowing
which one it is, and a name carries no thesis. Everything that constitutes a claim is
excluded by construction.

### What the delta looks like

On the sample deck the two routes overlap on 29% of the competitors they name. The cold
pass alone surfaces:

| Found only when the deck was out of the room | Why the directed pass missed it |
|---|---|
| **ServiceNow** | The deck never mentions it, so nothing prompted a search |
| **Systems integrators and BPO firms** | Deliver the same outcome as a service; not "software competitors" |
| **Internal platform teams** | Build-it-in-house is not a company, so it appears on no competitive matrix |

Plus two headwinds the directed pass never raised — that failed deployments usually
fail on process definition rather than tooling, and that mid-market ops teams often
have nobody to own an automation programme after go-live.

Those are not exotic findings. They are the obvious things an analyst covering the beat
would say, and the claim-directed pass could not reach any of them.

### Finding nothing is also a result

When the cold pass surfaces nothing new, the report says so explicitly rather than
leaving an empty section — because "the deck's framing did not steer the research away
from anything material" is a real and reassuring finding.

### What it does not establish

The cold pass may be wrong. It has no way to know which of its findings matters to
*this* company, and it has not read the deck, so it cannot tell you whether an omission
was negligent or sensible. What the delta establishes is narrower and still useful:
**the deck's framing narrowed the search, and by this much.**

## The problem with comparing two modes that read different sources

`--mode both` runs the three-agent pipeline and a single-prompt baseline so they can be
compared. Until now each ran its own searches, which made the comparison meaningless:

> "The pipeline found more risks" might only mean "the pipeline happened to retrieve a
> page about risks."

Any difference in output was confounded by a difference in evidence.

## The fix: a frozen corpus

Research runs **once**. The results are screened, frozen, and both modes read the
identical bytes. What remains between them is the thing under test — how the evidence
was processed.

```bash
deckscope run deck.pdf --mode both        # shares one corpus automatically
```

The report states which case you are in, and does not paper over the bad one:

```
evidence    corpus 01e5e4490b9c291e · 12 source(s)
            IDENTICAL for both modes
```

If the corpora differ, the comparison says **"NOT SHARED — comparison is confounded"**
rather than presenting the numbers as though they meant something.

### Corpora are reproducible

```bash
deckscope run deck.pdf --save-corpus evidence.json
deckscope run deck.pdf --corpus evidence.json     # replays, no new research
```

This is what turns a prompt change from an anecdote into a measurement. Edit a prompt,
replay the same evidence a week later, and the difference you see is the difference you
made — not what the web said that day.

The fingerprint is a hash of the source **content**, sorted, so it is stable across
query ordering and survives a save/load round trip. Two runs sharing a fingerprint read
exactly the same sources.

A corpus records what was **retrieved**, not merely what survived: a source dropped by
the security screen stays in it, marked and explained.

## Metrics that do not reward verbosity

The first version of the comparison counted claims, citations, risks and blind spots.
That rewards saying more, whether or not what you say is more correct — a mode that
emits twenty uncited claims would beat one that emits two well-supported ones.

So counts were replaced by **rates and matched differences**:

| Metric | Why |
|---|---|
| **Citation density** | Fraction of claims carrying a source, not how many citations in total |
| **Uncited assertion rate** | Stated directly, because an assertion resting on nothing is the failure the bibliography exists to catch |
| **Evidence-quality mix** | How the mode graded its own support |
| **Unique findings** | Claims one mode raised and the other did not — **matched on content** using the same aligner the panel uses, so a rephrasing counts as the same claim rather than as a discovery |
| **Contradictions** | The same claim, assessed differently, from the same evidence. The most interesting output of the whole comparison |
| **Cost** | Tokens, calls and seconds, alongside the quality signals rather than hidden |

### It still refuses to name a winner

None of this establishes which analysis is *better*. That needs decks with known
answers or a blinded human rubric, and DeckScope ships neither. The output says so:

> This measures DIFFERENCE, not correctness. Two runs of the SAME mode will also
> differ, so treat a single comparison as one observation rather than a result.

**What is now possible that was not before:** run the comparison across many decks on
frozen evidence, and the differences start to mean something in aggregate. That is the
evaluation harness the project still needs — but the confound is gone, which was the
thing preventing it from being built.
